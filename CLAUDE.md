# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Offline analysis for [LeetCodeBot](https://github.com/xDDoubleTea/LeetCodeBot), which lives in `~/programming/LeetCodeBot`. Two pieces of work: the statistics of problem description lengths (`findings.md`, for a course report), and a prototype of the planned `/suggest` problem ranking (`problem_ranking.ipynb`). Python 3.13, managed with `uv`.

## Commands

```bash
uv run findings_stats.py                # every number in findings.md, by section
uv run test.py                          # the three description-length charts
uv run jupyter lab                      # open problem_ranking.ipynb
uv run jupyter nbconvert --to notebook --execute --inplace problem_ranking.ipynb
uv run leetcode_auth.py                 # signed-in submission history -> cache/submissions.json
```

`problems.csv` is written by `export_csv.py`, which imports the bot's own parser, so it runs from the bot checkout with the bot's venv:

```bash
cd ~/programming/LeetCodeBot && .venv/bin/python ~/programming/leetcodebot-analysis/export_csv.py
```

## Data

Everything reads the bot's test database, `~/programming/LeetCodeBot/db/testbot.db`, by absolute path. It holds test data only. To pull the latest problems into it, run `LeetCodeProblemManager.refresh_cache()` from the bot checkout against that file.

`cache/` is gitignored and regenerated by the notebook: the AC rates it fetches from LeetCode (`ac_rate.json`) and each user's full ranking as CSV.

`leetcode_auth.py` signs in with the user's browser cookies, `LEETCODE_SESSION` and `CSRFTOKEN`, read from `.env` (gitignored) and fetches their whole submission history through GraphQL `submissionList` into `cache/submissions.json`. The REST `/api/submissions/` endpoint throttles with HTTP 403 partway through paging, so it is not used. Never print, log or commit the cookie values; when a probe needs the session, import `load_env` and redact the values from anything shown.

## Rules

**Update `findings.md` whenever `problems.csv` changes**, in the same commit. Run `uv run findings_stats.py`, copy the numbers into every section, and regenerate the charts with `uv run test.py`. Copy the old CSV aside first if its numbers might still be needed.

Section 4 of `findings.md` uses the CSV's `markdown_length`, the length after the 4,000-character cap, with population moments. Every other Markdown length is uncapped. `findings_stats.py` already does this; keep the two consistent.

Timings are re-measured on every run. Medians are stable; maxima vary by several times between runs.

## `desc_parser.py`

A vendored copy of the bot's description parser, so nothing here imports the bot. The bot's import chain reaches `config/secrets.py`, which needs a configured environment.

- `parse_problem_desc` and its helpers are copied from the bot's `utils/embed_presenters.py`. Re-copy them when the bot's parser changes, or results drift from what the bot does.
- `parse_problem_desc_uncapped` is the same parser without the 4,000-character truncation, to measure what the cap discards.
- `parse_problem_desc_bs4` is the parser from before the bot's PR #29 (commit `800f375^`, cut-off 800). It is fixed history, kept for timing against the current parser.

## `problem_ranking.ipynb`

Implements the proposal at <https://hackmd.io/@Kawaii-kanataso/problem-ranking-system>. The proposal's text is kept as written; cells headed **Implementation note** mark where the code interprets or departs from it, and the **Personalization options** section records variants tested but not implemented.

The ranking deliberately favours tags and difficulties the user already solves: fewer context switches, mastery of related concepts, and it moves on by itself as related problems run out. Treat variants that push users toward weak tags or harder problems as optional, not as fixes.

The user may have the notebook open in JupyterLab. Edit it with `nbformat` in place rather than regenerating it, so their edits survive, and tell them to use *File → Reload Notebook from Disk* afterwards.

LeetCode returns `status: null` for another user's problems without that user's session cookie, so solved and attempting status are not available for them. Signed in, `status` is `"ac"`, `"notac"` or `null` for the user's own problems.

**This repository is public and the notebook is committed with its outputs.** Showing individual submissions from the signed-in history is fine, failed ones included; the user decided that on 2026-10-18. Submitted code is never fetched, and the cookie values are never printed. Cells that read `cache/submissions.json` skip when the file is missing.
